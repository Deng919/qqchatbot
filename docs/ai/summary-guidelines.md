 # 摘要生成规范

 ## 适用范围

 本文档规定 AI 对各分类群聊生成日报摘要时的行为标准。群分类定义见 [group-taxonomy.md](group-taxonomy.md)。Prompt 组装规则见 [prompt-template.md](prompt-template.md)。

 ## 通用规则（所有分类适用）

 ### 基本原则

 1. **只基于输入消息生成摘要，不得编造、补充或推断未提及的内容。**
 2. 如果当天消息不足 5 条有效讨论，`main_topics` 可以为空数组，不要把单条消息拆成一个话题。
 3. 如果消息完全是闲聊或系统通知，摘要允许为空，但 `group_id` 字段必须始终返回。

 ### 字段语义

 | 字段 | 语义 | 边界 |
 |------|------|------|
 | `main_topics` | 当天讨论的主要话题，每个话题有独立主题 | 一条消息不算话题，至少 3 条相关消息才能构成话题 |
 | `conclusions` | 讨论得出的判断或共识 | 不是事实陈述，不是个人观点，必须是讨论后达成的结论 |
 | `resources` | 当天分享的可访问资源 | 必须有可访问的链接；纯文字推荐不含链接的不放这里 |
 | `tasks` | 有人承诺要做的行动 | 必须有明确执行人或隐含执行人，模糊意愿不算 |
 | `open_questions` | 提出但未解决的问题或争议 | 必须是讨论中出现的问题，不是 AI 自行提出的 |

 ### 人称与时态

 - 摘要用客观第三人称描述，不使用"我""我们""大家"。
 - 结论用已完成时态："已确认""已决定""已排除"。
 - 任务用将来时态："计划实现""预计完成""将提交"。

 ### 长度约束

 | 模板 | `main_topics` 每条 summary | `conclusions` 每条 | 其他字段每条 |
 |------|--------------------------|-------------------|-------------|
 | `concise` | 不超过 30 字 | 不超过 25 字 | 不超过 20 字 |
 | `detailed` | 不超过 80 字 | 不超过 60 字 | 不超过 40 字 |

 超出长度时优先保留信息密度最高的部分，不要截断成无意义片段。

 ## 分类策略

 ### `tech` 技术群

 **话题识别：**
 - 一个技术话题至少包含：问题描述 + 方案讨论 或 选型对比 + 结论。
 - 只记录技术结论，不记录 debug 过程中的试错步骤。
 - 如果讨论了多个技术点但互相独立，分别作为独立话题。

 **内容处理：**
 - 代码片段、命令行、配置内容不放入 `summary`，只记录"用什么解决了什么问题"。
 - 工具推荐必须标注用途：不能只说"推荐 XX"，要说"用于解决 YY"。
 - 报错日志不放入摘要，只记录报错的根因和解决方案。

 **结论判定：**
 - 技术选型讨论的结论：选了什么、为什么、排除了什么。
 - 问题排查的结论：根因是什么、怎么修的。
 - 架构讨论的结论：采用了什么方案、关键取舍。

 **排除：**
 - 一次性的环境配置问题（除非有通用解法）。
 - "我也遇到了""我也试试"等无信息量回应。

 ### `resource` 资源群

 **话题识别：**
 - 不按时间线组织，按资源类别分组（教程、工具、文档、开源项目）。
 - 同类资源合并为一个话题，不把每个链接单独列为话题。
 - 对资源的评价讨论可以构成话题。

 **内容处理：**
 - 每个资源在 `resources` 中记录：标题、链接。
 - 如果群友对资源有评价，放入对应话题的 `summary`。
 - 重复分享的同类资源只保留一个，在 summary 中注明"多人推荐"。

 **结论判定：**
 - 资源的质量评价共识：是否推荐、适合什么场景。
 - 资源对比结论：A 比 B 好在哪。

 **排除：**
 - 临时活动页面（报名链接、限时优惠）。
 - 需要登录或加群才能查看的内容。
 - 纯新闻资讯（无复用价值）。

 ### `project` 项目群

 **话题识别：**
 - 按需求点或任务模块组织，不按时间线。
 - 需求讨论、排期确认、进度汇报各为独立话题。
 - 阻塞和风险问题单独列为话题，不混入进度。

 **内容处理：**
 - `tasks` 必须标明隐含执行人："张三负责实现 XX"。
 - 截止日期如果消息中提到，必须记录在 task 描述中。
 - 决策记录放入 `conclusions`：决定了什么、为什么。

 **结论判定：**
 - 需求确认结论：最终确定了什么需求。
 - 排期结论：什么排到什么时间。
 - 方案选择结论：选了哪个方案、关键取舍。

 **排除：**
 - 具体代码实现细节（属于代码审查，不属于摘要）。
 - 日常进度打卡（"今天做了 XX"）除非有阻塞或风险。

 ### `study` 学习群

 **话题识别：**
 - 按知识点或题目组织，不按时间线。
 - 同一知识点的讨论合并为一个话题。
 - 错题和易错点单独列为话题。

 **内容处理：**
 - 知识点讲解记录结论和关键推导，不记录完整过程。
 - 错题记录：错在哪、正确思路是什么。
 - 学习计划归入 `tasks`。

 **结论判定：**
 - 知识点共识：正确解法是什么、易错点在哪。
 - 学习方法结论：什么方法有效。

 **排除：**
 - 具体题目答案（时效性短，除非有通用解法）。
 - 个人学习打卡记录。
 - 考试时间提醒（属于系统通知）。

 ### `general` 通用群

 **话题识别：**
 - 标准从严：至少 5 条相关消息才构成话题。
 - 如果一天内没有形成任何话题，`main_topics` 返回空数组。
 - 不要把单条有信息量的消息强行包装成话题。

 **内容处理：**
 - 单条消息不超过一句话概括。
 - 如果有个别有价值但不足以构成话题的内容，可以放入 `resources` 或 `tasks`，不要强行放入 `main_topics`。

 **结论判定：**
 - 通用群的结论标准更高：必须是多人讨论后达成的明确判断。
 - 个人观点不算结论。

 **排除：**
 - 群内梗和内部笑话。
 - 回应性内容（"对""同意""+1""哈哈"）。
 - 需要知道前因后果才有意义的片段。

 ## 上下文截断处理

 当消息总长度超过 `max_context_chars` 时，系统会自动截断保留最近的消息。此时 AI 会收到一个 `数据质量` 提示。

 AI 在截断情况下的行为要求：
 1. 摘要只覆盖实际收到的消息，不要假设被截断的内容。
 2. 如果截断导致对话不完整，在对应话题的 summary 末尾标注"[上下文不完整]"。
 3. 候选筛选标准不变，不要因为数据少就放宽标准。

 ## 空摘要处理

 当有效消息不足时，AI 必须返回合法的空结构：

 ```json
 {
   "group_id": 123456789,
   "main_topics": [],
   "conclusions": [],
   "resources": [],
   "tasks": [],
   "open_questions": [],
   "candidates": []
 }
 ```

 不要为了"看起来有内容"而把闲聊填充到话题或结论中。
