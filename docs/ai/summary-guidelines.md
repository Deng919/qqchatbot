 # 摘要生成规范

 ## 适用范围

 本文档规定 AI 对各分类群聊生成日报摘要时的行为标准。群分类定义见 [group-taxonomy.md](group-taxonomy.md)。Prompt 组装规则见 [prompt-template.md](prompt-template.md)。

 ## 通用规则（所有分类适用）

 ### 基本原则

 1. **只基于输入消息生成摘要，不得编造、补充或推断未提及的内容。**
 2. 两条及以上有信息量的往来可以形成话题；单条完整公告或重要事件也可以形成话题。
 3. 如果消息完全是闲聊或系统通知，`overview` 使用一句客观说明，`main_topics` 可以为空数组，但 `group_id` 必须始终返回。

 ### 字段语义

| 字段 | 语义 | 边界 |
|------|------|------|
| `overview` | 当天最值得知道的事 | 通常 1 至 2 句，不重复罗列所有话题 |
| `main_topics` | 有实际信息价值的话题 | 不设最低数量；临时邀约、短期推广和重复感叹不独立成话题 |
 | `conclusions` | 明确决定或经验证的结果 | 不是未经核实的外部事实或个人观点，不重复主要话题 |
 | `resources` | 当天分享的可访问资源 | 必须有可访问的链接；纯文字推荐不含链接的不放这里 |
 | `tasks` | 有人明确承诺的未来行动 | 必须有明确执行人或隐含执行人，正在做的事和模糊意愿不算 |
 | `open_questions` | 有后续价值的未解决问题或争议 | 必须是讨论中出现的问题，不罗列普通闲聊疑问 |

 ### 语言与事实边界

 - 用简洁、自然、中性的中文直接陈述内容，不使用“群内围绕……展开讨论”等固定套话。
 - 区分群友观点、群友转述和已核实事实。政策、健康、价格和数字等外部事实，若只有群友说法，标明“群友称”或“未经核实”；无原文或可靠链接时不得写“已确认”。
 - 对健康症状等可能涉及因果关系的内容，时间先后不能当作成因证据；只写观察和转述，不擅自归因。
 - 同一事实不要在概览、话题和结论中重复；任务只有确实承诺的未来行动。

 ### 自适应篇幅

 `main_topics` 每条 summary 只写理解话题所需的事实、不同观点和当前状态，不设固定字数；一句能说清就只写一句。消息密度和讨论深度决定报告长度，不设置精简或详细模式。相近消息合并。

 ## 分类策略

 ### `tech` 技术群

 **话题识别：**
 - 一般技术讨论应包含问题与方案，或选型对比与结论；单条完整的版本发布、故障通告或安全公告可独立成话题。
 - 只记录技术结论，不记录 debug 过程中的试错步骤。
 - 如果讨论了多个技术点但互相独立，分别作为独立话题。

 **内容处理：**
 - 代码片段、命令行、配置内容不放入 `summary`，只记录"用什么解决了什么问题"。
 - 工具推荐必须标注用途：不能只说"推荐 XX"，要说"用于解决 YY"。
 - 报错日志不放入摘要，只记录报错的根因和解决方案。

 **结论判定：**
 - 技术选型讨论的结论：选了什么、为什么、排除了什么。
 - 问题排查的结论：根因是什么、怎么修的。
 - 架构讨论的结论：采用了什么方案、关键取舍。

 **排除：**
 - 一次性的环境配置问题（除非有通用解法）。
 - "我也遇到了""我也试试"等无信息量回应。

 ### `resource` 资源群

 **话题识别：**
 - 不按时间线组织，按资源类别分组（教程、工具、文档、开源项目）。
 - 同类资源合并为一个话题，不把每个链接单独列为话题。
 - 对资源的评价讨论可以构成话题。

 **内容处理：**
 - 每个资源在 `resources` 中记录：标题、链接。
 - 如果群友对资源有评价，放入对应话题的 `summary`。
 - 重复分享的同类资源只保留一个，在 summary 中注明"多人推荐"。

 **结论判定：**
 - 资源的质量评价共识：是否推荐、适合什么场景。
 - 资源对比结论：A 比 B 好在哪。

 **排除：**
 - 临时活动页面（报名链接、限时优惠）。
 - 需要登录或加群才能查看的内容。
 - 纯新闻资讯（无复用价值）；完整的重要事件或公告除外，可简要记录其已知影响。

 ### `project` 项目群

 **话题识别：**
 - 按需求点或任务模块组织，不按时间线。
 - 需求讨论、排期确认、进度汇报各为独立话题。
 - 阻塞和风险问题单独列为话题，不混入进度。

 **内容处理：**
 - `tasks` 必须标明隐含执行人："张三负责实现 XX"。
 - 截止日期如果消息中提到，必须记录在 task 描述中。
 - 决策记录放入 `conclusions`：决定了什么、为什么。

 **结论判定：**
 - 需求确认结论：最终确定了什么需求。
 - 排期结论：什么排到什么时间。
 - 方案选择结论：选了哪个方案、关键取舍。

 **排除：**
 - 具体代码实现细节（属于代码审查，不属于摘要）。
 - 日常进度打卡（"今天做了 XX"）除非有阻塞或风险。

 ### `study` 学习群

 **话题识别：**
 - 按知识点或题目组织，不按时间线。
 - 同一知识点的讨论合并为一个话题。
 - 错题和易错点单独列为话题。

 **内容处理：**
 - 知识点讲解记录结论和关键推导，不记录完整过程。
 - 错题记录：错在哪、正确思路是什么。
 - 学习计划归入 `tasks`。

 **结论判定：**
 - 知识点共识：正确解法是什么、易错点在哪。
 - 学习方法结论：什么方法有效。

 **排除：**
 - 具体题目答案（时效性短，除非有通用解法）。
 - 个人学习打卡记录。
 - 考试时间提醒（属于系统通知）。

 ### `general` 通用群

 **话题识别：**
 - 优先识别有实际信息增量的讨论，不以固定消息条数作为唯一门槛。
 - 两条及以上有信息量的往来可以构成话题。
 - 单条消息只有在本身构成完整公告、结论或重要事件时才作为话题。

 **内容处理：**
 - 单条完整公告或重要事件按已知事实概括背景和当前状态，信息不足时保持简短。
 - 如果有个别有价值但不足以构成话题的内容，可以放入 `resources` 或 `tasks`，不要强行放入 `main_topics`。

 **结论判定：**
 - 通用群的结论标准更高：必须是多人讨论后达成的明确判断。
 - 个人观点不算结论。

 **排除：**
 - 群内梗和内部笑话。
 - 回应性内容（"对""同意""+1""哈哈"）。
 - 需要知道前因后果才有意义的片段。

 ## 上下文截断处理

 当消息总长度超过 `max_context_chars` 时，系统会自动截断保留最近的消息。此时 AI 会收到一个 `数据质量` 提示。

 AI 在截断情况下的行为要求：
 1. 摘要只覆盖实际收到的消息，不要假设被截断的内容。
 2. 如果截断导致对话不完整，在对应话题的 summary 末尾标注"[上下文不完整]"。
 3. 候选筛选标准不变，不要因为数据少就放宽标准。

 ## 空摘要处理

 当有效消息不足时，AI 必须返回合法的空结构：

 ```json
 {
   "group_id": 123456789,
   "overview": "当天消息主要为闲聊，没有形成可归纳的实质讨论。",
   "main_topics": [],
   "conclusions": [],
   "resources": [],
   "tasks": [],
   "open_questions": [],
   "candidates": []
 }
 ```

 不要为了"看起来有内容"而把闲聊填充到话题或结论中。
