# 候选审核原文上下文设计

日期：2026-09-25

## 目标

审核候选时，现有“原文摘录”可能只有十余字，无法判断短句在回应什么。已确认采用固定邻近消息方案：显示每条候选引用的原始消息，以及该消息前后各两条同群聊天。已有候选也应立即受益，不重新生成摘要。

## 数据来源与边界

`candidates.message_ids` 是候选引用的消息 ID；`messages` 归档库保存原文、群 ID、时间和发送者。打开候选详情时，后端根据候选 ID 查候选记录，再仅在候选所属群中定位这些消息。客户端不得指定群 ID 或任意消息 ID。对每条找到的引用，按 `(timestamp, msg_id)` 的稳定顺序各取前后两条；合并重叠结果并按时间排序。最多展示 40 条，先按时间保留引用消息，再用邻近消息填满剩余名额；若引用本身超过 40 条，也只展示时间最早的 40 条并明确提示。单条文字最多返回 2000 字，截断时标明，防止超长消息撑满页面。

缺失的引用不伪造原文：接口返回缺失数量，界面提示对应原消息未在归档中找到，并保留现有 `excerpt` 作为历史回退。原始引用消息本身只有短句时，也如实显示，邻近消息为理解语境提供帮助，不把邻近消息误标为候选证据。

## 接口与界面

沿用需登录的 `GET /api/candidates/{candidate_id}`，增加 `source_context`、`source_context_truncated` 和 `missing_source_count` 字段，不改数据库结构或摘要生成流程。`source_context` 每项包含消息 ID、时间、发送者、文本、是否为候选引用、文本是否截断。保留既有 `excerpt` 和 `message_ids` 字段供兼容。

审核详情把单行“原文摘录”升级为“原文与上下文”区域，逐条显示时间、发送者和原文，引用消息有明显标识，邻近消息用次级样式。长列表在详情面板内滚动。所有消息内容按纯文本插入 DOM，不解释 HTML；移动端仍可阅读。没有可用归档消息时显示原摘录和缺失提示。

## 验证

先写失败测试，再实现。覆盖同群隔离、前后边界、多个引用的重叠去重、稳定时间顺序、引用优先与 40 条上限、缺失引用回退、超长文本截断、未登录拒绝和 HTML 转义。全套测试后在真实浏览器检查候选详情的桌面及手机宽度、长列表滚动和关闭交互。不触发 AI 请求，也不改变候选审核动作。
