# 群聊收件箱 UI 设计

用户于 2026-10-18 在三套可点击原型中选择 B「群聊收件箱」。本次按已选布局实现，保留项目现有能力。

## 解决的问题

页面缺少稳定的阅读位置，操作、筛选和内容挤在一起。新的主流程是：左侧选群，中间看讨论列表，右侧读当前要点，需要时打开同一位置的完整报告或原消息。

## 已选布局

- 全站采用浅灰蓝的固定左侧导航。主入口、收藏／知识／待办等现有能力位置固定，开关仍生效；维护和设置保留。
- 摘要页采用讨论列表与阅读详情两栏，加左侧导航形成三栏。今日、七天、历史和高级日期筛选保留，但自定义筛选默认折叠。
- 列表使用真实摘要要点，点击后在右侧显示全文、群名、日期、来源、收藏、已读和完整摘要操作；仅查看不自动标为已读。
- 桌面默认选择当前页第一条，返回、筛选、翻页、切群时不会残留其他范围的内容。手机默认列表，点击才进入详情，提供明确的返回入口。
- 群侧栏复用现有 `/api/groups`；点击群准确筛选，空选择、禁用群和旧报告范围不扩大。列表内搜索明确只过滤本页，不假装全库搜索。
- 生成、重新生成、问答、来源核对、历史版本、知识保存等使用原有服务；不新增付费调用、数据模型或消息处理行为。

## 工程约束

现有 FastAPI/Jinja/原生 JS/CSS，不增加依赖。新样式只调整展示，新收件箱控制器接在已有异步结果校验后，保留 URL、阅读状态和请求令牌。对不支持加载的新面板不写入生产数据。基于明确的新布局更新已有导航测试，其他兼容行为保持。

## 验收

验证首条选择、窄屏不自动进详情、切群／日期／分页清空旧内容、迟到读状态返回、完整报告返回、来源和收藏开关、长群名与长正文、无结果和加载失败。运行相关回归、全量 Python 与全部前端脚本，独立 Chromium 在 1440 和 390 宽度下操作，最后核对桌面包与入口。正式数据和配置不纳入 Git。
