# 修复后继续检查：待办异步完整性

基线 `0e4e561`。用户要求继续检查优化，沿用自主修复与隔离工作区约定。

已复现：正式待办提交 A 后继续输入 B，A 成功回调删除整个草稿，刷新显示 A；从原消息创建后关闭并打开另一来源，旧成功回调无条件关闭新面板；待办编辑提交 `expected_revision=2**63` 触发 SQLite OverflowError。

采用现有 taskDrafts 与 taskPanelToken，不引入通用表单框架。保存回调只清除与已提交值一致的草稿；更新值不同则保留输入，采用本次成功返回的 revision/status，继续手动保存。保存等待期间再次列表重建仍只允许一个该任务保存请求；完成请求不能清除新输入。创建成功总是反馈实际已创建任务，但仅在面板 token 仍相同时关闭及调整地址／视图；提交使用捕获的来源，旧响应不影响新面板。字段编辑仍允许，采用输入禁用会限制现有体验且不能解决列表重建的异步分支，因此不选。

API 用已有范围校验拦截 SQLite 整数越界，服务直接调用也拒绝越界 revision。检查同待办模块任务路径、原消息群号是否存在同类可复现问题，修复限定为该模块，不建立新的验证抽象。

独立复核确认另一交叉分支：A 保存后列表重建，新表单输入 C，旧请求 409 回调读旧表单并覆盖当前草稿、显示旧表单的核对入口。处理方式是只标记当前 Map 草稿冲突，以任务 ID 定位当前卡片的核对按钮；不从脱离页面的表单回写字段。成功仅采用保存返回版本，不采用之后列表中的更高版本自动重基。

验收：真实模板 DOM 延迟 promise 回归；真实 API 输入与服务校验；现有待办与内容专项、全量 Python/CJS；独立 Chromium 验证延迟保存输入和旧响应新面板。只用合成数据。代码复核通过后合入主项目并沿用本机版本交付流程。原配置、数据、未跟踪文件和 Codex 进程保持不动。
