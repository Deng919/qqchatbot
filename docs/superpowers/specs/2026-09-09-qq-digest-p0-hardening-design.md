# QQ Digest P0 渐进式加固设计

## 背景

QQ Digest 已具备 NTQQ 数据库刷新与采集、SQLite 归档、每日摘要、候选审核、知识库写入、Web 管理和 QQ Bot 通知能力。当前主要风险不是基础功能缺失，而是摘要内容在数据流中丢失、噪声进入模型上下文、单群失败中断整批任务、Web 操作互斥规则不一致，以及报告覆盖写入缺少原子保护。

本阶段采用渐进式加固：保留现有架构、配置格式、CLI、数据库和页面导航，只在问题所在的边界增加小型、可测试的组件。手动范围总结、报告档案升级、跨期汇总、知识库工作台和分块摘要不属于本阶段。

## 目标

1. Markdown 报告完整保留结构化摘要中的话题说明和资源描述。
2. AI 上下文与确定性提取使用同一套消息清洗规则。
3. 清理已知 QQ 平台噪声、HTML 实体和无价值内部链接，同时保留用户消息的来源标识。
4. 单个群摘要失败后继续处理其他群，并返回可观察的部分成功结果。
5. 让部分成功任务能够按现有重试机制再次执行，已成功且输入未变化的群不重复调用模型。
6. 用统一任务协调器管理刷新、采集、同步和日报冲突。
7. 报告文件写入失败时保留上一份有效文件，不留下临时文件。

## 非目标

- 不重构整个 `qq_digest/web/app.py`。
- 不改变现有报告命名和每群每日一份报告的约束。
- 不增加新的前端页面或修改导航结构。
- 不改变密钥、配置文件或 NTQQ 解密流程。
- 不实现 token 级分块、跨期汇总或知识库索引。

## 摘要保真与消息清洗

### 数据模型

`Resource` 增加可选 `description` 字段。报告渲染同时接收话题标题与说明、资源标题与说明，不再把结构化对象提前降级成只含标题的字符串。

结构化响应继续允许兼容提供商返回额外字段。本阶段不启用全局 `extra="forbid"`，避免已有兼容接口因非关键扩展字段突然失败；对程序依赖的字段仍由 Pydantic 严格校验。

### 清洗规则

`Preprocessor` 成为摘要上下文与确定性提取的共同入口。每条消息按以下顺序处理：

1. 解码 HTML 实体并规范化空白。
2. 丢弃空消息及现有系统噪声规则命中的消息。
3. 识别 URL，移除结尾标点，规范化主机名大小写，并按规范化结果去重。
4. 从“确定性资源链接”中排除已知 QQ 平台内部资源，例如表情、拍一拍和装扮商城地址。
5. 保留清洗后的消息文本及对应消息 ID、时间、发送者，使候选仍能追溯来源。

内部 URL 只从确定性资源清单中排除；如果一条用户消息还包含自然语言内容，该内容仍进入模型上下文。纯平台噪声消息可以整体丢弃。

### 上下文构建

上下文窗口从清洗后的消息行构建。截断策略本阶段保持“按完整行保留最近消息”，但质量说明增加原始消息数、纳入消息数和丢弃消息数，为后续分块摘要提供可观察指标。

### Markdown 渲染

- 话题渲染为 `- **话题**：说明`；说明为空时只显示话题。
- 资源渲染为带链接标题，并在存在描述时追加说明。
- JSON 报告保持完整结构化数据。
- 现有章节顺序和文件路径保持不变。

## 单群故障隔离

采集仍然先覆盖所有启用群，再开始调用 AI。摘要阶段为每个群建立独立异常边界：

- 成功：写入报告、候选和通知，记录在 `succeeded_groups`。
- 输入未变化：跳过 AI，记录在 `skipped_groups`。
- 失败：不写报告、不删除旧候选，记录群 ID、群名和清洗后的错误摘要，然后继续下一个群。

`DailyRunResult` 增加成功、跳过和失败群信息。只要存在失败群，总任务状态记为 `partial_success`；全部成功或正常跳过时记为 `success`。只有流水线级错误（例如归档数据库不可用）才抛出异常并记为 `failed`。

调度器只把 `success` 视为当天完成。`partial_success` 计入尝试次数并按现有间隔重试；重试时已成功群由输入指纹跳过，因此不会重复调用模型或重复通知。

Web 手动运行接口对部分成功返回正常 JSON，包含 `status` 和失败群明细，不把已经产生报告的结果包装成笼统 HTTP 500。页面 toast 显示成功与失败数量。

## 统一任务协调器

新增独立的 `OperationCoordinator`，集中保存活动任务集合及冲突矩阵。所有检查和登记在同一事件循环同步片段内完成，并通过异步上下文管理器保证退出时释放状态。

冲突规则：

| 操作 | 与其冲突的操作 |
| --- | --- |
| `refresh` | `refresh`、`collect`、`sync`、`daily` |
| `collect` | `refresh`、`collect`、`sync`、`daily` |
| `sync` | `refresh`、`collect`、`sync`、`daily` |
| `daily` | `refresh`、`collect`、`sync`、`daily` |

本阶段采取保守的全互斥规则，因为刷新会替换解密数据库，而日报可能在同一运行中刷新、采集和摘要。以后拆出只读归档摘要后，再考虑按群并行。

协调器提供快照给现有状态 API，保持页面需要的 `*_running` 语义。后台循环在无法取得操作权时跳过当前轮次，不排队堆积；用户触发的接口返回 HTTP 409 和当前占用操作。

## 报告原子写入

`ReportWriter` 对 Markdown 和 JSON 分别执行：

1. 在目标文件同目录创建命名临时文件。
2. 写入、`flush` 并 `fsync`。
3. 两个临时文件都准备成功后，再用 `os.replace` 替换目标文件。
4. 任一步骤失败都清理尚存临时文件。

为了保护一对已有报告，替换前为现有目标创建同目录备份；两个目标都替换成功后删除备份。若第二次替换失败，则从备份恢复已替换的目标。数据库报告记录只在文件写入成功后更新。

该方案不改变现有文件名，同时保证常见异常和被测试的失败点不会把一对有效报告变成不匹配状态。进程在极小的双文件替换窗口内被强制终止仍无法获得真正的跨文件系统事务；不可变版本报告将在后续报告模型升级中解决这一限制。

## 错误与日志

- 面向用户的失败信息包含群名和可行动的错误摘要，但不包含 token、原始私聊内容或完整上游响应。
- 日志记录异常类型和群 ID，保留堆栈用于本机诊断。
- 清洗统计只记录数量，不记录被丢弃的消息正文。
- 原子写入错误明确指出 Markdown 或 JSON 阶段，同时保持旧文件可读。

## 测试策略

所有生产改动遵循红—绿—重构：

1. 摘要模型测试：资源描述被保留；话题说明进入 Markdown。
2. 预处理测试：HTML 实体解码、URL 规范化、内部链接排除、自然语言保留、噪声丢弃。
3. 上下文测试：模型收到的是清洗后消息，质量统计反映丢弃数量。
4. 流水线测试：中间群 AI 失败时后续群仍生成报告；部分成功重试不会重复成功群。
5. 调度测试：`partial_success` 会重试，`success` 不重试。
6. 协调器测试：每种冲突都被拒绝，异常退出后状态释放。
7. Web 测试：冲突返回 409；部分成功返回明细。
8. 文件测试：Markdown 或 JSON 准备/替换失败时旧文件不变且无临时文件残留。
9. 完整回归：运行全部 pytest；如页面文案或行为变化，再执行桌面和移动端浏览器冒烟验证。

## 兼容与迁移

`jobs.status` 为文本列，无需数据库结构迁移即可保存 `partial_success`。现有 `success` 和 `failed` 记录继续有效。新增结果字段只扩展 API，不删除现有字段。

现有配置、SQLite 文件、报告文件、知识库、CLI 参数和 QQ Bot 指令均保持兼容。部署不需要用户手工迁移数据。

## 完成标准

- 结构化摘要中的话题说明和资源描述出现在新生成的 Markdown 报告中。
- AI 上下文不再包含已识别的纯 QQ 平台噪声，确定性链接不再列出已知内部资源。
- 一个群摘要失败时，其他群仍能完成，页面能看到失败群。
- 部分成功任务会重试且不会重复处理输入未变化的成功群。
- 任一受控报告写入失败后，旧 Markdown/JSON 内容保持一致，临时文件被清理。
- 所有任务冲突通过统一协调器执行，没有分散且不一致的状态判断。
- 完整测试套件通过，且不修改本阶段非目标中的外部行为。
