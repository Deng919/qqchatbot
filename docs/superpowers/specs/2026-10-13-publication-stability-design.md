# 报告发布与桥接文本稳定性

目标：已生成的摘要遇到短暂 Windows 文件访问冲突时能完成发布；损坏的桥接字节流不能静默进入报告。

证据：10 月 13 日增量生成在 `os.replace` 出现 WinError 5，再次生成成功。已确认异常发生在文件发布阶段；具体占用进程未查明。当前代码立即回滚，用户重试会再次调用 AI。桥接解码使用 `errors="replace"`，不可解码字节可变成替换字符；原 GB18030 成功测试外层 JSON 使用默认 ASCII 转义，未真正覆盖非 ASCII stdout。

方案比较：重跑完整生成会重复调用 AI；建立持久化重试队列增加状态和恢复成本。选择在现有文件事务中对替换操作有限重试，保持原事务边界。

- `reports.py` 的安装和回滚共用文件替换函数，只重试 Windows 错误 5、32、33，最多三次，等待 0.1、0.2 秒；其他错误立即抛出。持续失败按现有流程保留旧文件和数据库版本。
- `ai/bridge.py` 接受 UTF-8 或严格 GB18030；都无法解码时抛出不含正文的 AIError。合并非零退出和空 stdout 的重复错误解析。合法 stdout 不因非结构化 stderr 警告而失败。
- 不增加后台任务、设置项、依赖或 AI 重试，不修改账号池与模型选择。

验收：故障注入验证首次冲突恢复、持续冲突回滚、回滚期间冲突恢复和非 Windows 错误不重试；编码测试使用真正非 ASCII 字节，并验证损坏输出不被接受。运行发布、修订、流水线、桥接相关测试及全量回归。

按用户既有自主执行及隔离工作区要求，在当前会话执行并本地集成。数据完整性审计只读；若发现历史摘要覆盖差异如实记录。
